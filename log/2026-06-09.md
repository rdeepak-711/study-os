Day 2. Extended the gate-slice into a full CRUD on the `entries` app, no AI writing the code. Added three routes for a single id on top of yesterday's POST and GET:

- **GET `/entries/{id}`**: SELECT where id, `fetchall()`, if nothing came back raise `HTTPException` 404, else return the row.
- **PUT `/entries/{id}`**: UPDATE entries SET text WHERE id, then check `mycursor.rowcount`. If 0 rows were affected the id didn't exist, so raise 404. Otherwise commit and return the id.
- **DELETE `/entries/{id}`**: DELETE FROM entries WHERE id, same rowcount check, 404 if nothing was deleted.

Where I froze tonight was different from day 1. The SQL and syntax came back fine. What got me were concepts. First I tried to reuse GET-one as a 404 check by calling it from inside PUT and DELETE, and it silently did nothing, because I didn't `await` it. An async function returns a coroutine that never runs unless you await it. Awaiting it worked, but it was the wrong shape anyway: a hidden second query before every update/delete. The right tool was `rowcount`, which tells you how many rows the statement actually touched, so one query both does the work and tells you whether the id existed. Also learned `lastrowid` only means something after an INSERT, not after an update or delete.

Smaller things I had to fix on review: wrong verb on update (POST instead of PUT), returned `rowcount` as if it were the id, left "created" in the update and delete messages, and an untyped path param made the id come back as a string in one route and an int in another.

Ran all five routes before calling it done: create, list, read one, update, delete, and confirmed a missing id returns 404 instead of crashing. Day 1 was syntax recall. Day 2 was framework concepts. The freeze is shrinking.
